# Research: Mondel

## MLflow integration

- **Decision**: Implement an `MlflowRunGateway` behind a backend interface using the MLflow Python client (MLflow 2.x+). Resolve all active MLflow Experiment IDs, then list non-deleted Run candidates with `search_runs`, `max_results=20`, `order_by=["attributes.start_time DESC", "attributes.run_id ASC"]`, and an opaque `page_token`. Apply a safely constructed case-insensitive Run-name substring filter when requested. Map Experiment IDs to their names and return both with each candidate. Load a selected Run with `get_run` and dataset inputs from `RunInputs.dataset_inputs` when the tracking server supports it. For a terminal Run, canonicalize each `(metric key, step)` group by retaining the observation with the greatest timestamp and, when that timestamp is also tied, the greatest numeric value. Select the maximum canonical `accuracy`, breaking ties by the smallest step, then retain only canonical Metrics at that selected step. Histories used during capture are discarded rather than persisted.
- **Rationale**: Paging prevents the selector from loading every Run and maps directly to MLflow's `PagedList` token. Stable newest-first ordering makes recently started training easy to find, while Run ID distinguishes duplicate or missing Run names. MLflow permits a Metric to be logged multiple times and records timestamp and step for each observation; the canonicalization rule makes duplicate input deterministic and follows MLflow's latest-timestamp, then maximum-value tie behavior. `Run.data.params` is the complete MLflow parameter map, while `Run.data.metrics` only exposes latest values and cannot identify the metrics at the best-accuracy step. The accuracy history is therefore required to select that step, but storing every observation would duplicate MLflow and inflate MySQL and API responses. Dataset inputs retain MLflow dataset metadata such as name, digest, source and schema; this is more reliable than an application-specific tag convention.
- **Alternatives considered**: Returning every Run in one response was rejected because response time and browser rendering would grow with tracking history. Numbered pages and a total count were rejected because MLflow natively provides an opaque continuation token and not a stable total. Reading only `Run.data.metrics` was rejected because it cannot meet the multiple-accuracy requirement. Browser-to-MLflow access was rejected because it leaks external configuration and bypasses API validation.

## Backend execution model

- **Decision**: Use synchronous SQLAlchemy 2.x with PyMySQL and the synchronous MLflow Python client. FastAPI path operations and dependencies that perform these blocking I/O calls use normal `def`, with one SQLAlchemy Session per request. Complete any required MLflow retrieval before opening the database transaction that persists a new snapshot and association.
- **Rationale**: The initial MVP is a low-concurrency, single-team learning application. A synchronous request flow makes API, service, database, commit, and rollback behavior easier to trace while still allowing FastAPI to execute blocking path operations in its thread pool. Keeping external MLflow waits outside the database transaction avoids holding database connections and locks during network I/O.
- **Alternatives considered**: Asynchronous SQLAlchemy and an async MySQL driver were deferred because they add coroutine, async session, driver, and async-test concepts before the core HTTP and transaction flow is understood. Reconsider asynchronous data access only if measured concurrency or latency shows that the synchronous thread and connection pools are a bottleneck.

## Evolution Step list pagination

- **Decision**: Use keyset pagination for `GET /evolution-steps`, ordered by `(created_at DESC, id DESC)` with a fixed page size of 20. Read at most 21 rows; return the first 20 and emit an opaque `pageToken` containing the last returned `(created_at, id)` only when the extra row proves that a next page exists. A continuation query selects rows where `created_at` is older than the cursor, or where `created_at` is equal and `id` is smaller. Reject malformed tokens with `422`.
- **Rationale**: Both ordering fields are immutable, so editing an existing Evolution Step does not move it between pages. `created_at` expresses the user-facing newest-created-first order, while `id` makes equal timestamps deterministic. A newly inserted item belongs before an existing cursor and therefore does not appear halfway through an already-started traversal; reloading the list starts a fresh traversal.
- **Alternatives considered**: Returning all Evolution Steps was rejected because response and rendering cost would grow with the planned 1,000-Step dataset. Offset pagination was rejected because inserting a new leading item can shift offsets and create duplicates between requests. Ordering by `updated_at` was rejected because ordinary edits would move existing items across page boundaries. ID-only ordering could work with the current generated IDs, but it makes chronological behavior depend on identifier allocation rather than the explicit creation timestamp.

## Snapshot and service boundary

- **Decision**: Separate a mutable `RunReference` from an optional immutable `RunSnapshot`. Linking a Run always persists its reference after confirming that the Run exists in MLflow. A `RUNNING` or `SCHEDULED` Run remains snapshot-pending. A `FINISHED`, `FAILED`, or `KILLED` Run is terminal and causes its Parameters, best accuracy, selected best step, Metrics recorded at that step, dataset inputs, status, execution timestamps, and raw metadata to be captured once. The detail page first loads local data, then automatically calls a separate Run synchronization action for each linked Run and lazily loads the stored best-step Metrics. Synchronization updates the reference's current name, current status, and timestamp; if a pending Run has become terminal, it also creates the snapshot and child rows in one transaction. A finalized snapshot is never overwritten.
- **Rationale**: Developers can link a Run when long-running training starts and cannot forget which Evolution Step it belongs to. The association is useful immediately, while comparison evidence becomes available only when the Run reaches a terminal state. Keeping the first detail read local preserves responsiveness and outage tolerance; using a separate synchronization action makes the network call and database mutation explicit.
- **Alternatives considered**: Requiring a terminal Run before linking was rejected because multi-hour training makes delayed manual association easy to forget. Capturing a `RUNNING` Run immediately was rejected because it permanently freezes incomplete Metrics and Dataset inputs. Polling MLflow in a background worker was deferred because it introduces scheduling, retry, and operational concerns not needed for the initial MVP. Refreshing a finalized snapshot was rejected because it could rewrite historical conclusions. Resuming a finalized Run may change its live status, but a separately tracked continuation should use a new Run ID and Evolution Step.

## Data persistence

- **Decision**: Use MySQL 8.0+ and SQLAlchemy 2.x with normalized `evolution_step`, a singleton `lineage_mutation_guard`, `run_reference`, optional one-to-one `run_snapshot`, `run_parameter`, `best_step_metric`, `dataset_input`, and append-only `evolution_step_history` tables. Save the current MLflow name, status, execution times, and synchronization timestamp on `run_reference`; save finalized values and capture time on `run_snapshot`.
- **Rationale**: The relational schema makes result-Run ownership enforceable and keeps the selected best-step Metrics queryable without duplicating every observation already owned by MLflow. JSON payload columns retain unmodeled MLflow metadata for troubleshooting without becoming the comparison source.
- **Alternatives considered**: A graph database is unnecessary for the expected bounded MVP graph. Storing only JSON prevents indexed uniqueness and simple, deterministic comparisons.

## Result Run exclusivity and lineage validation

- **Decision**: Place a nullable unique constraint on `evolution_step.result_run_id`, with both Run-link foreign keys referencing `run_reference.run_id`. Every transaction that can mutate a Run link first locks the singleton `lineage_mutation_guard` row, then locks its target Evolution Step, reads the latest complete edge set, substitutes the proposed links, and runs deterministic depth-first cycle detection by Run ID. All mutation paths use this lock order. The database unique constraint remains the final protection against concurrent result-Run claims.
- **Rationale**: An Evolution Step represents an edge `$parentRun \rightarrow resultRun$`. A cycle exists exactly when the proposed directed Run graph cannot be topologically traversed. Locking only the edited Evolution Step would allow concurrent requests on different rows to validate against different incomplete states and commit a cycle. The shared guard makes the second request wait and then validate against the first committed result. Acquiring the guard before any target-row lock avoids circular lock ordering, and the transaction automatically releases it on commit or rollback.
- **Alternatives considered**: Checking only direct parent/result equality misses multi-generation cycles. Locking only the target row does not serialize graph-wide validation. A process-local mutex fails when multiple application processes are used, and a MySQL named lock is connection-scoped rather than transaction-scoped. Locking a seeded singleton row is explicit and automatically follows transaction lifetime. Cascading child updates violates FR-024.

## Differences

- **Decision**: Treat Parameters as string key/value maps. For the union of keys, return `added` when only the result contains a key, `removed` when only the parent contains it, and `changed` when both values differ. For metric key exactly `accuracy`, compare each Snapshot's stored best accuracy and return `$resultBest - parentBest$`; return an explicit unavailable reason if either value is missing. Pair Dataset Inputs by `(context, name)` when that key is unique within each Run. For a pair, compare `digest`, `sourceType`, and `source`; return only differing pairs as `changed`, unmatched recorded inputs as `parent_only` or `result_only`, and omit unchanged pairs. Mark the Dataset comparison unavailable when either Run has no Dataset Inputs or a duplicate pairing key makes the mapping ambiguous.
- **Rationale**: This directly implements FR-012, FR-014, FR-015, and FR-016 without inferring optimization direction for other metrics. Dataset terms describe differences between MLflow input records and avoid claiming row-level additions or removals that cannot be derived from metadata alone.
- **Alternatives considered**: Comparing latest accuracy would produce the wrong result for non-monotonic training. General metric selection or min/max heuristics are explicitly out of scope. Pairing Dataset Inputs by capture order was rejected because order is not a stable identity. Treating an unmatched input as rows added or removed was rejected because a digest indicates that data differs but does not identify individual row changes.

## Lineage response

- **Decision**: Derive Lineage from current Run links and center every response on the requested Evolution Step. Return the selected Step separately, ancestors nearest-first, and descendants breadth-first with Evolution Step ID ascending inside each generation. Every Lineage Step carries `distanceFromSelected` and `parentEvolutionStepId` in addition to its purpose, hypothesis, and parent/result Run summaries. Do not create a dedicated external-root field: a non-null parent Run with no producing Evolution Step marks the upstream boundary, while a null parent Run means no upstream Run exists.
- **Rationale**: A selected-centered response supports the initial ordered-list UI and lets users follow both directions without redefining the actual Lineage root. Explicit distance and parent-Step identity preserve branches and can also feed a future graphical view without making the MVP implement graph layout.
- **Alternatives considered**: Root-first ancestor ordering was rejected because the selected Step is the user's current point of interest. A nested descendant tree was rejected because deeply nested response types complicate clients and future pagination. A special external-root object was rejected because the earliest Step's parent fields already distinguish an unregistered upstream boundary from an absent parent.

## API and frontend state

- **Decision**: Version FastAPI routes under `/api/v1`. React uses React Router for list, create, and detail pages and a hand-written typed wrapper around browser `fetch` for API calls. Each feature explicitly manages loading, success, empty, and error states and refreshes affected data after mutations. The detail page renders the local detail response first, calls `POST /runs/{runId}/sync` for each linked Run, and reloads local detail when synchronization succeeds. The frontend displays snapshot-pending states, `409` integrity violations, and non-blocking `502` synchronization warnings.
- **Rationale**: The HTTP/OpenAPI contract is the sole cross-stack boundary. Using browser `fetch` keeps the request and response flow visible during learning, while the small typed wrapper prevents duplicated URL and error-handling code. The frontend remains responsible for usability and local form feedback; FastAPI remains the authority for constraints.
- **Alternatives considered**: TanStack Query was deferred because its caching and server-state abstractions would hide the initial request-state flow and add a library before the MVP needs advanced cache behavior. Generated OpenAPI clients were deferred so the first API types and calls remain inspectable. Duplicating lineage checks in React was rejected because clients can be stale and constraints must hold for all callers.

## Testing

- **Decision**: Test pure diff and graph functions with pytest unit tests; test MySQL constraints, migrations, transactions, and FastAPI responses against a dedicated MySQL test database; mock the MLflow gateway for active linking, terminal snapshot capture, best-accuracy ties, best-step Metric selection, repeated synchronization, Run-name changes, incomplete data, and failures; verify that finalized snapshots are inserted once, omit full Metric histories, and are never overwritten; validate OpenAPI against API responses; introduce Vitest and React Testing Library with the frontend to test loading, pending, synchronized, error, empty, warning, and constraint states; add one Playwright end-to-end test for the critical create-and-attach flow after frontend/backend integration.
- **Rationale**: The highest-risk rules are graph integrity and external-service failure, both of which need verification below the browser and across the HTTP boundary.
- **Alternatives considered**: Testcontainers was deferred because automatic container lifecycle management adds another abstraction before database integration testing is understood; the test database connection is supplied explicitly instead. Playwright is used for the critical end-to-end user flow and representative validation errors, while exhaustive validation cases are covered by faster backend integration and frontend component tests to avoid duplication. Manual-only validation is rejected by the constitution and cannot reliably cover concurrent ownership or all cycle shapes.
